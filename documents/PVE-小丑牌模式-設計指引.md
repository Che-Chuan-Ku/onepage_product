# PVE（小丑牌模式）設計指引與引擎評估

> 撰於 2026-07-07。基於現況掃描：規則引擎全在後端（Java 21 / Spring Boot 3.2，`SeriousDuelService.java` 761 行、`PushResolver.java`、`FieldGenerator.java`），技能為硬編碼 enum（2 職業、6 技能，switch-case 分派），前端 Next.js + React 純渲染（Canvas 2D + 自寫 rAF 特效佇列，Zustand），specs/plans 中無任何 PVE/roguelike 既有規劃。

---

## 一、小丑牌（Balatro）到底是什麼在好玩

拆解它的成功要素，才能判斷哪些移植得過來：

| 要素 | Balatro 的做法 | 本質 |
|---|---|---|
| 核心動詞極簡 | 出撲克牌型得分 | 玩家 3 秒懂規則，深度全在修飾層 |
| 乘法式增益堆疊 | Joker 對「籌碼 × 倍率」做修飾 | 組合爆炸：150+ Joker 兩兩相乘產生無限 build |
| 目標是「分數門檻」而非「打倒對手」 | Blind 要求分數指數成長 | 逼玩家滾雪球，build 成長曲線可被數值調控 |
| 局間抉擇 | 商店買 Joker/卡包/重抽 | 策略層與操作層分離，每次進商店都是決策點 |
| 一局短、死了重來 | 單場 2–5 分鐘，一輪 30–60 分鐘 | 「再來一局」的成癮節奏 |
| 內容 = 資料 | Joker 多數只是「觸發條件 + 數值修飾」 | 加內容的邊際成本趨近於零 |

**關鍵洞察：Balatro 不是「對戰遊戲加了 roguelike」，它是「計分遊戲加了修飾器市場」。** 五子棋是二元勝負（贏/輸），沒有連續的分數軸——這是移植時最大的結構性差異，必須先解決。

## 二、移植優劣分析

### 優勢（你的底子其實非常好）

1. **既有資產映射度極高**：
   - 主動技能（6 種）→ 消耗型卡牌／充能技能
   - 場地效果（火山噴發、海灘漲潮）→ Balatro 的 Stake/Blind 變體（每關規則突變）
   - 隱藏格機制 → roguelike 的風險回報語彙（你們的創新性分析文件已自己註記到這點）
   - `PushResolver` 連鎖推擠引擎 → 現成的「效果結算原語」，是效果系統的地基
2. **PVE 解掉 PVP 的死穴**：對戰遊戲沒有玩家池就是死局。PVE 給了單人留存與內容深度，讓遊戲「沒人在線也好玩」，反過來養 PVP 玩家池。這是策略層面最大的收益。
3. **PVE 容忍失衡**：真劍勝負在 PVP 下每個技能都要精密平衡；PVE 反而「越壞越好玩」——玩家湊出 broken combo 是爽點不是 bug。你可以把 PVP 不敢上的瘋狂效果全部倒進 PVE。
4. **後端權威引擎可直接複用**：規則已 100% 在 Java 後端，PVE 只是把「對面的人」換成 AI + 把「一場」換成「一輪 run」，`SeriousDuelService` 的技能結算、場地結算大多可抽出重組。

### 劣勢與風險（按嚴重度排序）

1. **【高】沒有分數軸**：五子棋連成五就結束，沒有「build 滾雪球」的空間。→ 解法見第三節的 Boss HP 模型。
2. **【高】沒有 AI 對手**：現在是純 PVP，PVE 的工程關鍵路徑就是棋 AI。帶技能與場地效果的五子棋無法直接套現成 minimax（技能會打破搜索假設）。→ 解法：啟發式威脅評估（活三/衝四偵測）+ 淺層搜索即可，**難度靠給 AI 作弊條件（修飾器）調，不靠搜索深度**——這正好和 Balatro 的 Blind 設計同構。
3. **【高】單場時長不匹配**：15x15 標準五子棋一場 10–30 分鐘，Balatro 單場 2–5 分鐘。一輪 run 若 8 關就是 2 小時起跳，節奏死掉。→ 解法：PVE 用小棋盤（9x9/11x11）+ 手數預算制。
4. **【中】技能系統是硬編碼 enum**：現在加一個技能要改 `SkillType.java` + `SeriousDuelService` 的 switch-case。Balatro 式玩法需要幾十上百個修飾器，這個架構加 10 個內容就會失控。→ 必須先重構為資料驅動（第四節）。
5. **【中】五子棋本身理論上先手必勝**：純規則下有解。但技能+場地+修飾器已經打破這點；PVE 下更無所謂。列出來只為說明：**不要在 PVE 保留 Swap2 這類平衡機制**，它們是 PVP 專用的。

## 三、建議的 PVE 核心循環：「Boss HP × 連線計分」模型

把「連成五贏」改成「**連線 = 造成傷害**」，就同時解掉分數軸與時長兩個問題：

```
一關（Encounter）：
  Boss 有 HP（如 300）。你有手數預算（如 30 手）。
  每完成一條線（五連為主，可設計四連小傷害）→ 結算傷害 → 該線棋子移除（棋盤局部清空）→ 繼續落子。
  傷害 = 基礎值(線長/棋子種類) × 遺物倍率 × 場地加成
  手數用完 Boss 沒死 → run 結束（或扣命）。

一輪（Run）：
  8–10 關，Boss HP 指數成長（複製 Balatro 的門檻曲線）。
  關與關之間進商店：買主動技能、被動遺物、場地改造、重抽。
  3 關一個 Boss 關：Boss 帶規則突變（見下）。
  全程 15–25 分鐘。
```

這個模型的好處：
- **連線後清除棋子**＝棋盤自我更新，單關不會下滿收攤，節奏可控（單關 2–4 分鐘）。
- 傷害公式天生就是 Balatro 的「籌碼 × 倍率」，遺物有明確的掛載點。
- AI 對手可以降格為「干擾者」（Boss 每 N 手落一子擋你/推你），AI 難度需求大幅降低——它不用會贏，只要會煩。第一版甚至可以做成純無對手的 score attack，AI 之後再上。
- 你現有的場地結算（每 10 手海浪、噴發清 8 格）直接變成關卡機制，零改動複用。

### 三軸內容體系（保持正交，內容才能相乘）

| 軸 | 對應 Balatro | 例子（用你現有機制延伸） |
|---|---|---|
| 主動技能（卡牌，消耗/充能） | 消耗牌 | 現有 6 技能直接搬；橫斬變成「清一行並計傷」 |
| 被動遺物（Joker） | Joker | 「你的推擠連鎖 +1 格」「噴發不影響你的棋子」「每第 5 手落子變爆彈」「斜線傷害 ×2」 |
| 場地/Boss 突變（Blind/Stake） | Blind debuff | 「本關禁用橫向連線」「每 5 手噴發一次」「海側每回合侵蝕」「棋盤 9x9」 |

**規則：三軸的效果全部用同一組原子操作實作**（落子、移除、推移、變換、生成、傷害修飾）。`PushResolver` 已經是其中一個原語，把它擴成完整的效果原語庫。

### 其他設計要點

- **種子化 RNG**：後端引擎全程用 seeded random（`FieldGenerator` 現在的隨機生成要改為吃 seed）。這給你每日挑戰、run 分享、bug 重現三個功能，成本只是一個參數。
- **Meta 進度**：職業/技能/遺物用「解鎖」制發放（現有 WARRIOR/ARCHER 是頭兩個職業），解鎖條件綁成就。這是留存的主引擎。
- **平衡策略**：PVE 不追求平衡，追求「門檻曲線調對」。先讓玩家能 broken，再調 Boss HP 曲線讓 broken 剛好夠用。
- **PVP 反哺**：PVE 驗證過受歡迎的技能/遺物，挑保守版本下放到真劍勝負，內容管線單向流動（PVE 實驗場 → PVP 精選）。

## 四、工程路線圖（依賴順序）

```
M0 效果系統重構（前置，最重要）
    把 SkillType enum + switch-case 重構為：
    效果 = 觸發器(trigger) + 條件(condition) + 原子操作序列(ops) + 數值(params)
    定義為資料（JSON/YAML 或 DB 表），引擎只實作原子操作。
    驗收：現有 6 技能 + 2 場地效果全部改為資料定義，PVP 行為不變（回歸測試）。
M1 計分關卡引擎
    Boss HP、傷害結算、連線清除、手數預算。單關可玩（無商店無 AI）。
M2 Run 循環 + 商店
    關卡序列、門檻曲線、局間商店、遺物掛載。
M3 干擾型 AI / Boss 行為
    啟發式落子（威脅評估）+ Boss 突變規則。
M4 Meta 進度 + 每日挑戰
    解鎖系統、seeded 每日 run、排行榜。
```

M0 是唯一「不做後面全部會塌」的步驟；M1–M2 完成即有可玩垂直切片，可以開始給人試。


**升級路徑（如果將來 Canvas 真的不夠）**：
- 特效變重 → 在 React 內換 **PixiJS**（WebGL 渲染）或 Phaser，只換渲染層，其他全留。成本是 Unity 重寫的 1/10。
- 要上 Steam/桌面 → **Tauri/Electron** 包殼，web 技術棧原封不動。
- 要上 App Store → 先用 PWA 或 Capacitor 包殼驗證，真有原生需求再議。

**唯一該考慮 Unity 的情境**：轉型做重度視覺特效/3D 表現、以主機/手把為主要平台、或團隊已有 Unity 人力。目前三者皆否。

**一個真正值得注意的架構問題**（比換引擎重要）：PVE 單人模式若沿用後端權威，每一手都要打 API——伺服器成本與延遲都跟著玩家時長走（你部署在 Render 上）。短期沿用後端沒問題（複用引擎、防作弊、排行榜可信）；若日後 PVE 玩家時長起量，再評估把「資料驅動效果引擎」的解譯器在 TypeScript 端實作一份供單機 run 使用（M0 做對的話，效果定義是資料，兩端共用同一份定義檔，只需要兩個解譯器）。這是把 M0 做成資料驅動的第二個理由。

## 六、風險與開放問題

- **連線清除後的棋型設計**是新玩法的手感核心，需要 prototype 驗證：清整條線？清五顆？留一顆錨點？建議 M1 階段用最快的方式（甚至純後端 CLI/測試腳本）試三種變體。
- 傷害公式的數值曲線沒有先例可抄，Balatro 的指數曲線（每 Ante ×1.6~2.5）可當起點。
- AI 即使是干擾型，也要避免「感覺是隨機亂下」——最低限度要會擋活三。
- 現有 PVP 的每技能限用一次（`SeriousDuelService.java:240-242`）在 PVE 應改為充能/消耗制，注意不要讓兩模式共用這段邏輯時互相污染——M0 重構時把「使用限制」也做成資料欄位。
