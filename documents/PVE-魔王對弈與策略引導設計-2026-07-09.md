## 1. 魔王關（對弈）系統設計

### 1.0 為什麼要新增 EncounterType

現有 `PveEncounter` 只有一種玩法：預放黑子雛形＋補完＝扣 Boss HP。魔王對弈的核心不同點——**存在一個會反擊的對手**、**沒有 HP／沒有場地/突變**、**勝負是連五而非扣血歸零**——用同一套 `finishSettlement`（`totalDamage>0→扣血`、`bossHpCurrent<=0→CLEARED`）硬套會出現語意錯誤（對弈根本沒有「傷害」）。因此新增：

```java
public enum PveEncounterType { PUZZLE, DUEL }
```

`PveFieldScheduler.encounterTypeFor(sequence)`：sequence∈{4,8}→`DUEL`，其餘→`PUZZLE`。DUEL 關的 `fieldType=PLAIN`、`mutationType=NONE`（見下方理由）、不產生任何 `PlannedCell`（無預放黑子、無場地格）。

**為什麼 DUEL 關不疊加 VOLCANO/BEACH/突變**：對弈本身的公平性論證（§1.7）已經是本設計最脆弱的一環（啟發式 bot、非搜尋），此時再疊加場地隨機噴發/潮汐/突變去扣玩家或 Boss 的棋子，會讓「誰赢是因為下得好」還是「誰赢是因為場地隨機幫了誰」變得無法歸因，也讓 §4 的統計測試失去可重複性（同一 BossAiPolicy 版本因場地 RNG 而勝率飄動）。魔王關的複雜度應該全部來自「對弈本身」，不是疊加消線關的花俏機制。

### 1.1 棋盤與先後手

沿用 `PveFieldGeometry.BOARD_SIZE=11`。**玩家＝黑子＝先手**（維持現有 `PveBoard.tsx` 「PVE stones 一律渲染黑子」的既有語意，也符合自由五子棋「先手有結構性優勢」的公平性直覺——這正是讓 L4≥70%/L8≥45% 這種偏向玩家的目標在數學上有立足點的原因，見 §1.7）。**Boss＝白子＝後手**，白子語意沿用現有 `PveBoard.tsx` 對 `obstacles` 陣列裡白子的既有渲染路徑（見 §5.2 frontend diff 的視覺缺口修補）。

### 1.2 Boss AI 決策表（可實作規格）

**威脅分類（AI 內部的形狀掃描函式，四方向：橫/縱/雙斜）**：對每個候選落點 `(r,c)`，試放該色棋子後，沿 4 個方向分別算「連續同色長度 `run`」與「兩端開放格數 `opens∈{0,1,2}」：

| 形狀 | 判定條件 | 意義 |
|---|---|---|
| 五連（勝） | `run≥5` | 立即獲勝 |
| 活四 | `run==4 且 opens==2` | 兩端都能補成五，無法同時擋兩端＝已經輸了 |
| 衝四 | `run==4 且 opens==1` | 只有一個缺口能補成五，擋住那一格即化解 |
| 活三 | `run==3 且 opens==2` | 兩端皆空，若不擋，下一手可能推成活四 |

**決策優先序（由上而下，命中即出手；每一層若有多個候選，見「延伸己線」段落的加權排序或隨機挑選規則）**：

1. **己方能直接五連（贏）** → 出手。
2. **擋玩家已成形的活四／衝四**（玩家現在任一候選格落子會產生 `win==true`，即玩家棋子已經擺出「補一手就贏」的四形）→ 擋掉那個致命缺口。此為**必擋**，兩檔難度都不可跳過（跳過＝Boss 主動放水輸掉，不允許）。**（2026-07-09 §6.4 L4 調校新增）** L4 有一個很小的機率（見 §1.3）改選這個缺口「附近」的候選格而非缺口本身（"手滑"）——這一層本身仍然存在、不是被跳過，只是 L4 偶爾選錯格。
3. **阻止玩家形成活四**：若玩家有候選格「落子後會產生活四」（`open_four==true`），必須在**該手發生前**攔截該格（因為活四一旦成形就有兩個必勝缺口，事後只能擋一個）。**（2026-07-09 §6.4 L4 調校）** 此層改為**僅 L8「真魔王」執行**；L4「見習魔王」完全不評估這一層（使用者裁決：「見習不該會預判」）——這是本輪唯一的無條件、不可用機率調整回補的層級移除，其餘 L4 調整都保留在機率層面。**（2026-07-09 §6.5 更新，取代上一句的「完全不評估」）** L4 改為 **8% 機率執行**此層（不再是硬性 0%）——見 §6.5，起因是「手數耗盡＝FAILED」改為「手數耗盡＝DRAW＋可重試」後，L4 不再需要靠「完全零預判」才能維持對一般玩家的可打性，保留一點點漏網之魚的機率，讓長期重複遊玩仍有新鮮感、避免固定死角被套路。
4. **己方形成活四** → 出手（等同己方也擺出不可擋的必勝形）。
5. **己方形成雙威脅**（一手同時製造 ≥2 條「活三或衝四」，對手無法同時化解全部）→ **僅 L8「真魔王」使用**；L4「見習魔王」永遠跳過此層（使用者裁決：「不會主動做雙威脅」）。
6. **擋玩家的活三**（阻止其推成活四）→ **L4 有機率跳過此層**（見下方§1.3；斜線方向的威脅額外加碼跳過機率），L8 恆定不跳過。
7. **延伸己線**：對每個候選格，評分 `= (若此手產生任一新威脅則+1) × 100 + 此手落子後己方最長連續長度`，取最高分；若有並列，從中依「離棋盤中心 Chebyshev 距離越近越優先」排序取前段再隨機挑一個（避免決策完全固定、每次都黏在同一路徑上，讓每盤棋仍有變化）。**（2026-07-09 §6.4 L4 調校新增）** 若最高分候選會構成「跨斜線方向的雙威脅」，L4 有 30% 機率改為純粹依「己方最長連續長度」（不看新威脅加成）重新評分，排除該斜線雙威脅候選——見習魔王自己的進攻也少用斜線雙線牽制。
8. **中心偏好**：以上皆無候選（極端情況）時，選離棋盤中心 Chebyshev 距離最近的空格。

**等效評分表**（給偏好「單一 evaluate() 函式取最大值」寫法的實作者，兩者擇一皆可，語意完全一致）：

| 優先層 | 條件 | 分數 |
|---|---|---|
| 1 | 己方落子後五連 | 1,000,000 |
| 2 | 擋玩家已成形之活四/衝四缺口 | 500,000 |
| 3 | 阻止玩家形成活四（預防性） | 200,000 |
| 4 | 己方形成活四 | 100,000 |
| 5（僅L8） | 己方形成雙威脅 | 50,000 |
| 6（L4機率跳過） | 擋玩家活三 | 10,000 |
| 7 | 延伸己線：`(新威脅?100:0) + 己方最長連續長度` | 0–104 |
| 8 | 中心偏好 tie-break | `-Chebyshev距中心` |

**候選格剪枝（效能考量，非規則本身）**：只評估「距任一現有棋子 Chebyshev 距離 ≤2」的空格，棋盤全空時退化為天元 `(5,5)`（11×11 中心）。這把每手的候選數量從最多 121 格降到通常 <40 格，4 方向×每格線掃描是 O(候選數) 的輕量運算，同步請求內完成綽綽有餘，不需要非同步/背景運算。

### 1.3 L4「見習魔王」vs L8「真魔王」參數表

**2026-07-09 大幅放水校準（§6.4）**：本表原始版本（2026-07-09 初版）只有「跳過活三機率」一個旋鈕。玩家 agent 真後端實測 5 連敗後，發現 L4 防守幾乎無漏洞（活四/衝四必擋、且會預判攔截活三成形），使用者裁決大幅放水，新增 4 個旋鈕（層 3 移除、層 2 手滑、層 6 斜線加碼、層 7 斜線雙威脅降頻）。第一輪參數（層3移除 + 跳過活三45% + 斜線加碼15pp + 手滑10%）統計測出對「普通玩家」(OrdinaryPlayerPolicy) 的 Boss 勝率只有 7.5%——見 §6.4 根因分析——因此跳過活三/手滑/斜線加碼三個旋鈕都對半下修，層3移除本身維持不變（使用者裁決「見習不該會預判」是無條件的，不因為統計不達標而回補）。下表是**校準後定案值**：

| 參數 | L4 見習魔王 | L8 真魔王 |
|---|---|---|
| 阻止玩家形成活四（層3，預防性攔截） | ~~完全不評估此層~~ **（2026-07-09 §6.5 更新）8% 機率執行**（原判給兩檔難度皆執行，§6.4 改為 L8 專屬／L4 完全不評估；§6.5 因「手數耗盡改判DRAW可重試」不再需要L4零預判來維持可打性，回補一個小機率） | 恆定執行 |
| 跳過「擋玩家活三」機率（層6） | **22%**（初版曾定 45%，見 §6.4 因與層3移除複合效應校準回 22%——比原始 20% 基準線略高，仍是有意義的放水） | 0%（恆定執行） |
| 斜線活三額外跳過加碼（層6） | **+8pp**（威脅只靠斜線方向成立時，跳過機率 22%+8%=30%；初版曾定 +15pp，同上下修） | 0（不適用） |
| 已成形活四/衝四「手滑」機率（層2） | **5%**（初版曾定 10%，同上下修；觸發時改選缺口附近的候選格，非缺口本身） | 0%（恆定精準擋） |
| 斜線雙威脅構線降頻（層7，己方進攻） | **30%**（最高分候選若含跨斜線雙威脅，30% 機率改用純長度評分排除它） | 0（不適用，L8 本就用層5主動做雙威脅） |
| 主動做雙威脅（層5） | 否（永遠跳過該優先層） | 是 |
| 其餘必擋層（五連/已成形活四衝四的主路徑） | 恆定執行，不受任何機率影響 | 恆定執行 |

### 1.4 開局腳本（棋譜庫 Section A 的降維延續）

沿用 `PVE-關卡重設計-2026-07-08.md` 已建立的方法論——「借用棋譜庫的幾何形狀，不借用其強制回應邏輯」——這裡改為借用 Section A 的**相對位形**（不是絕對座標，因為棋譜庫原座標基於 15×15 天元 `(7,7)`，PVE 是 11×11 天元 `(5,5)`，且玩家的第一手座標是自由選擇，不是固定的）：

- **L4：花月**（`gomoku-puzzle-library.md` A1：白2 與黑1 走「直指」正交緊鄰）。玩家的第 1 手（黑1，自由選擇座標 `(r,c)`）之後，**Boss 的第 1 手（全局第 2 手）腳本化**為 `(r+1, c)`；若 `r+1` 超出棋盤（`r=10`），改用 `(r-1, c)`。
- **L8：浦月**（A2：白2 走「斜指」對角緊鄰）。Boss 第 1 手腳本化為 `(r+1, c+1)`；任一座標越界則該軸改用 `-1` 方向（例如 `r=10` 時用 `r-1`，`c=10` 時用 `c-1`，兩軸各自獨立判斷）。
- **從 Boss 的第 2 手（全局第 4 手）起，完全轉為 §1.2 的 AI 政策**，不再腳本化。

**範疇誠實聲明**：棋譜庫 Section A 本身對「花月/浦月」只定義了黑1/白2/黑3 三顆子（即白方僅 1 手），且原文註明「非殺局謎題，無固定手順終局」——因此本設計把「前幾手腳本」具體落地為「Boss 的頭一手腳本化，其餘轉 AI」，而非虛構棋譜庫沒有記載的後續腳本手順。這是忠於素材庫既有內容的最小可行版本，符合 07-08 文件已建立的「不逐點複製、只借幾何精神」原則。

### 1.5 勝負判定

> **2026-07-09 §6.5 公平性修正（本節下方「手數耗盡」判定已被取代，見 §6.5）**：
> 本節原始版本把「手數耗盡」歸為「玩家敗」的一種，判 `FAILED`→整個 run 判負。
> 使用者裁決這對玩家不公平——只有玩家有手數配額、Boss 每手免費，雙方零失誤
> 卻讓玩家獨自承擔「下不完」的全部責任（L8 模擬耗盡率曾測到 44.2%，見
> §1.7）。**手數耗盡且雙方皆未連五，改判 `DRAW`（和局），不沒收 run、不計
> 敗，該關可原地無限次重試（每次重開盤面/Boss AI RNG 重新隨機）**——詳細
> 設計與實作校準見 §6.5。以下條列保留作為歷史記錄，「手數耗盡」小節的
> 判定結果以 §6.5 為準。

- **玩家勝**：玩家任一手後，四方向掃描出現 `run≥5`（含超五，沿用現有 freestyle 規則不額外排除長連）→ 該局立即 `CLEARED`。
- **玩家敗（可重試）**，二擇一：
  - **Boss 五連**：Boss 落子（含開局腳本手）後掃描出現 `run≥5` → `FAILED`。
  - ~~**手數耗盡**：`encounter.movesUsed >= encounter.moveBudget`（`movesUsed` 只計玩家自己的落子次數，沿用現有 `placeMove` 的既有計數語意不變；Boss 每次都是「玩家落子後立即在同一次請求內回應的免費一手」，不佔用玩家的手數配額）且尚未分出勝負 → `FAILED`。~~ **→ 改為 `DRAW`，見 §6.5。**

### 1.6 技能：真劍勝負的「智取」路徑

使用者裁決：「真劍勝負技能可用（帶入已購技能——技能就是智取路徑），Boss 不用技能」。逐一核對現有 6 個技能在 `executeSkill`（`PveChallengeService.java:304-394`）裡的既有語意，全部**天然適用**於對弈場景、不需要新增技能種類：

| 技能 | 現有語意 | 對弈關的智取用法 |
|---|---|---|
| 橫劈/縱劈 SLASH | 把錨點周圍棋子朝指定方向推 1 格 | 把 Boss 正在排列的連線推散，打斷其威脅形成——即使用者原文舉例的「對 AI 用橫劈破壞其連線」 |
| 精準狙擊 PRECISION_SNIPE | 把**現存白子**目標格直接轉成黑子（`stoneAt==WHITE` 才可選） | 對弈中「白子」就是 Boss 的棋子——本技能等同「策反」Boss 的一顆子，直接破壞其陣型同時累積己方連線，語意完全對應、**不需要後端改動** |
| 散射 SCATTER_SHOT | 兩發子（Chebyshev距≥2）**不計入 `movesUsed`** | 對弈中最強的「省手數」智取手段：等同白嫖 2 手免費落子而不消耗手數配額，可用來一次補完一條活三兩端 |
| 天地反轉 HEAVEN_EARTH_REVERSAL（大絕） | 指定方向的一個區域內，所有棋子**變色** | 把 Boss 一整叢即將成型的棋子直接反色成己方——保底大絕，用在 Boss 快形成雙威脅或活四時的最後手段 |
| 開拓之星 PIONEER_STAR（大絕） | 指定方向的一個區域內，所有棋子**移除** | 直接清空 Boss 那一叢棋子，比反轉更保守（不會意外幫自己拼出五連但也不會直接得分） |

**Boss 不用技能**：`useSkill` 端點維持「只有 `playerId` 持有的 `PveRunSkill`」這條既有查詢邏輯，Boss 沒有 `PveRunSkill` 記錄，天生無法呼叫此端點，**不需要額外程式碼去禁止 Boss 用技能**——這是現有架構的自然副產物，值得在實作 diff 中明講以避免有人誤以為需要加一道 guard。

**技能不觸發 Boss 回手**：`useSkill` 現行程式碼本就不遞增 `encounter.movesUsed`；比照 §1.5「Boss 只在玩家 `placeMove` 之後回手」的設計，`useSkill` 的對弈分支**不應該**觸發 Boss AI 計算（否則等於玩家每用一次技能，Boss 就白賺一手，等於變相懲罰用技能，違背「技能＝智取捷徑」的設計初衷）。這點在 §5.1 backend diff 明確列為一條獨立需求。

### 1.7 手數上限與公平性論證（誠實版）

**方法**：由於 `BossAiPolicy` 尚未寫成 Java，本文件用 Python 寫了一個**行為完全對應 §1.2 決策表**的啟發式 bot，讓「玩家方 bot」與「Boss 方 bot（分 L4/L8 兩組參數）」互打，跑蒙地卡羅統計，作為設計階段的**方向性 sanity check**，不是正式驗收（正式驗收見 §4，必須用真正的 `BossAiPolicy` 實作、且用更貼近「棋譜庫 VCF 強制手順」水準的參考玩家腳本）。模擬腳本：`scratchpad/boss_ai_sim4.py`（可重跑）。

**玩家 bot 的能力**：除了 §1.2 決策表同款的分層邏輯外，額外加了一個淺層「VCF 式」2手前瞻——嘗試找一個「己方衝四」，模擬 Boss 唯一合理的擋法後，檢查是否能接著形成雙威脅；若能，優先打這手（這是刻意模擬「玩家已經上過 1-7 關、學過強制手順技巧」的行為，比純粹貪婪的 1 手評估更接近真實水準，但**仍遠不及**棋譜庫 Section C 那種完整 VCF 搜索）。Boss bot 不具備此前瞻（符合「啟發式、非搜尋式」的裁決）。

**跑出來的數字（n=400–500 seed，總手數＝雙方合計）**：

| 局型 | 合計手數上限 | 玩家勝率 | Boss勝率 | 手數耗盡（未分勝負，算玩家敗） |
|---|---|---|---|---|
| L4（skip3=20%，無雙威脅） | 60 | 33.0% | 9.8% | 57.2% |
| L4 | 100 | 37.2% | 18.0% | 44.8% |
| L8（skip3=0%，有雙威脅） | 90 | 34.8% | 21.0% | 44.2% |
| L8 | 120 | 35.5% | 21.5% | 43.0% |

**誠實解讀**：

1. **這組數字沒有達到 70%/45% 的目標**，即使把手數上限拉到很寬鬆（100/120 合計手數，board 只有 121 格，這已經接近半盤）。玩家勝率在各種上限下都卡在 33–37% 左右、Boss 勝率 10–22%，其餘 43–57% 是「兩邊都太保守、遲遲分不出勝負」的手數耗盡。
2. **主要瓶頸不是「玩家會輸」，而是「遲遲下不完」**：把「手數耗盡」排除、只看已分勝負的局，玩家:Boss 的勝場比在各設定下大約落在 3.4:1（L4）與 1.5–1.7:1（L8）——方向正確（玩家明顯佔優，且 L4 優勢明顯大於 L8，與難度設計意圖一致），但耗盡率太高表示這個 Python 玩具 bot 依然遠不如「真正會下 VCF 強制手順」的玩家。
3. **根因推論（推論，非實證）**：雙方都只做 1–2 手前瞻的啟發式，在 11×11 空曠棋盤上很容易陷入「彼此都在防守對方剛冒頭的活三，誰都不主動鋪陳雙線」的僵局——這其實印證了使用者裁決背後的核心公平性機制：**Boss 被限定為純啟發式（不搜尋），而真人玩家經過 1-7 關訓練後執行的是有意圖的強制手順（VCF chain）**，這種「深度搜尋 vs 純啟發式」的不對稱才是設計要靠的獲勝槓桿，我這個玩具 bot 的「玩家方」也只做了淺層前瞻、遠不到真人玩家的水準，所以模擬出來的數字理當是保守下界，不是上界。
4. **待驗證事項（不可當作已知事實引用）**：L4≥70%／L8≥45% 這兩個數字目標，在本文件階段**尚未被證明可達成**，必須等 `BossAiPolicy` 真正實作、且 §4 的統計測試用一個確實執行棋譜庫 Section C 式強制手順搜索的參考玩家腳本重新測過，才能定論。若屆時測出來仍不達標，可調的旋鈕依優先序：① 拉高手數上限（本模擬顯示這仍有邊際效益）；② 讓 L4 也在「阻止玩家形成活四」這層加入一個更保守的機率跳過（目前恆定執行，若要再放水，這是唯一還沒動過的旋鈕，但這已經超出使用者裁決的「非致命威脅」範疇，需要回頭跟使用者確認是否allow）；③ 檢討候選格剪枝半徑是否讓 Boss 漏看太遠的威脅。

**手數上限的實作建議值（起始值，非最終值）**：既有架構的 `moveBudget` 語意只計玩家自己的落子（Boss 回手不算），故上表「合計手數」需要換算：

|---|---|---|
| L4 | **30** | ~60 |
| L8 | **45** | ~90 |

## 4. 測試策略

### 4.1 現有 harness 為什麼不能直接套用

`關卡可解性.feature`／`PveMutationRateStatisticsSteps` 這類既有測試的核心假設是「初始盤面固定、玩家依序補完所有雛形即可解，順序不影響結果」——這套「補完即解」模型完全建立在**沒有反擊**這個前提上（07-08 文件 §0 開宗明義就是靠這個前提才把棋譜庫降維使用）。DUEL 關卡沒有固定解——勝負是雙方交替落子的動態過程，「這一局解不解得開」這個問題本身沒有意義，必須改問「這個 BossAiPolicy 配置，對戰某個參考玩家，N 局裡贏率多少」。

### 4.2 統計測試設計（仿照既有 `Boss突變統計驗證.feature` 先例）

新增 `specs/features/pve/Boss對弈統計驗證.feature` ＋對應 `BossDuelStatisticsSteps.java`，結構完全比照現有 `PveMutationRateStatisticsSteps`（跑 N 個 seed、斷言比率門檻）：

- **參考玩家腳本**：**不能用本文件 §1.7 的 Python 玩具 bot 直接翻譯**，必須實作一個真正執行「棋譜庫 Section C 式 VCF 強制手順搜索」的 `ReferencePlayerPolicy`——即：每一手先找「是否存在一串衝四強制交換，最終逼出雙威脅或直接五連」的手順（搜索深度可設上限，例如比照 Section C7 的 10 手鏈長度，深度上限抓 12），找不到才退回 §1.2 同款的分層啟發式。這個「先搜 VCF 鏈、找不到才退化啟發式」的組合，比 §1.7 的 2 手前瞻更貼近真人玩家水準，也更貼近本設計「教玩家 VCF 概念、再讓玩家對戰不會搜索的 Boss」的核心賣點。
- **普通玩家腳本（2026-07-09 §6.4 新增）**：`OrdinaryPlayerPolicy`——不做 VCF/VCT 搜索，只有「擋魔王已成形活四/衝四、延伸自己最長線、簡單衝四完成」這幾個反射動作，刻意連「阻止對手形成活四」的預判都不做（對稱 L4 自己失去的層3）。這才是「見習」難度真正該測的對戰對象——量測方向與參考玩家統計相反：參考玩家統計問「玩家能不能贏 L4」，普通玩家統計問「L4 能不能贏普通玩家」（Boss 勝率）。
- **測試矩陣**：`N=200`（起始值，若方差過大需加大，由實測標準誤差決定，不得先射箭再畫靶把 N 訂低到剛好卡過門檻）；分別跑 `BossAiPolicy(APPRENTICE)` vs 參考玩家、`BossAiPolicy(TRUE_DEMON)` vs 參考玩家、`BossAiPolicy(APPRENTICE)` vs 普通玩家。
- **斷言門檻**：L4 局（vs 參考玩家）：玩家勝率 `≥70%`；L8 局（vs 參考玩家）：玩家勝率 `≥45%`；L4 局（vs 普通玩家）：**Boss 勝率 `≥60%`**（§6.4）。
- **輔助統計**（避免「贏是贏了，但贏得很難看／很僥倖」）：記錄每局手數分佈（p50/p90），若 p90 逼近 `moveBudget` 上限，代表預算太緊，需要調整§1.7末的建議值。
- **統計方法論陷阱（2026-07-09 §6.4 踩雷記錄）**：參考玩家統計沿用既有的「每格位重試至多3個候選 seed」機制（`RETRIES_PER_SLOT`）保護統計不被單一難搞 seed 誤傷——但這個機制若原封不動套用到普通玩家統計會**反向汙染**結果：重試只在「玩家輸」時觸發，等同給玩家 3 次機會（best-of-3），會系統性拉高玩家測得的勝率、壓低 Boss 測得的勝率。普通玩家統計因此改用不重試的單次測量（`simulateSingleAttempt`），因為這裡要測的正是 Boss 的真實單局勝率，不該讓玩家享有重試優勢。

## 6. 實作校準（2026-07-09 執行紀錄）

本節依 §1.7 誠實聲明的要求——「正式驗收必須等 `BossAiPolicy` 真正寫出來、且用一個真正會下『棋譜庫 VCF 強制手順』的參考玩家腳本跑 §4 的統計測試後才能定論」——記錄實作完成後的真實校準過程與最終數字，取代 §1.7 的模擬下界估計。

### 6.1 起始值不達標，兩輪校準

- **第一輪（僅拉高手數上限）**：`BossAiPolicy`/`ReferencePlayerPolicy`/DUEL 對局流程完整實作後，首次用 §1.7 建議起始值（`DUEL_MOVE_BUDGET = {4:30, 8:45}`）跑統計測試（先以 N=15 快速迭代，N=200 留待最終確認），得到 **L4 66.7%（10/15，未達70%）、L8 13.3%（2/15，遠低於45%）**。診斷：L8 對局的 `movesUsed` 大量卡在手數上限附近（p50=p90=45），與 §1.7 對玩具 bot 的觀察一致（「主要瓶頸不是玩家會輸,而是遲遲下不完」）。依文件已授權的第一個旋鈕（拉高手數上限）調整為 `{4:45, 8:70}`，重跑：L4 提升到 80%，**L8 幾乎沒變（13.3%）**——證實 §1.7 的推論成立：光靠餘裕手數救不了「雙方都太弱、下不出強制手順」的根本問題。
- **發現並修一個真實 bug（非校準，是正確性缺陷）**：追查「L8 對局停在 movesUsed≈61」時，發現 11×11=121 格棋盤在雙方都不主動求勝的僵局下會被下滿；`BossAiPolicy.nextMove`／候選格產生器（`PveDuelCandidates`）原本在候選池為空時一律回退「棋盤正中央」，未檢查該格是否已有棋子——近滿盤時會靜默覆寫既有棋子，等同棋盤損毀。修法：① `PveDuelCandidates.cells()` 候選池為空但盤面非全空時，先退化成「全盤掃描找任一空格」而非直接放棄；② `PveChallengeService.settleDuel` 在呼叫 Boss AI 前檢查 `SeriousBoard.isFull()`，全滿時直接判定 `ENCOUNTER_FAILED`（`MOVES_EXHAUSTED`），不進入 AI 選子。此修正本身不改變勝率（僵局盤面本來就該判負），只是讓判負方式從「靜默棋盤損毀」變成「乾淨的手數耗盡判定」。
- **第二輪（強化參考玩家：VCT-lite）**：真正的槓桿在參考玩家的搜尋深度。`ReferencePlayerPolicy` 原本的 VCF 搜尋只串接「衝四」強制交換——但 `BossAiPolicy` 對「活三形成」的防守本身就有機率性缺口（L4 20% 跳過、L8 從不跳過但仍只擋一端），純衝四鏈遇到「每四必被擋」的完美防守者會卡死。加入「VCT-lite」：搜尋樹額外納入「活三」型強制手（假設對手擋較靠近棋盤中心的那一端，L8 必定如此、L4 有 80% 機率如此——若假設在實際對局中落空，參考玩家下一個真實回合會用更新後、通常更有利的盤面重新搜索，不會造成傷害，只是偶爾偏保守）。加入後以 N=15 重跑：**L4 100%（15/15）、L8 100%（15/15）**，對局手數大幅縮短（movesUsed p50 從 60+ 降到 16–22）。

### 6.2 最終驗收數字（N=200，真實 BossAiPolicy vs 真實 ReferencePlayerPolicy，經以上校準後）

| 關卡 | 目標門檻 | 實測勝率 | movesUsed p50 | movesUsed p90 |
|---|---|---|---|---|
| L4 見習魔王 | ≥70% | **97.5%**（195/200） | 21 | 22 |
| L8 真魔王 | ≥45% | **100%**（200/200） | 16 | 21 |

### 6.4 L4「見習魔王」緊急放水校準（2026-07-09 二輪執行紀錄）

**起因**：§6.2 記錄的 97.5%/100% 數字看似達標，但用真玩家 agent 走真實後端連續對戰 L4 卻連敗 5 場（棋譜見 `scratchpad/pve-boss-playthrough/level-4/`）。診斷發現兩個問題：① `BossAiPolicy` 的層3（阻止玩家形成活四）與層2（擋已成形活四/衝四）100% 精準執行、完全無漏洞，"見習"魔王實際上打得比真魔王還嚴謹；② 用來做統計驗收的 `ReferencePlayerPolicy`（VCF+VCT-lite 強制手順搜索）遠強於一般玩法，97.5% 這個高勝率其實只證明「一個會強制手順的玩家能贏」，沒有回答「一般玩家覺不覺得 L4 好打」。

**使用者裁決的放水旋鈕**：(a) 完全移除層3「預防性攔截」（見習不該會預判）；(b) 層6「擋活三」跳過率 20%→45%；(c) 新增層2「手滑」：擋活四/衝四 10% 機率選次佳位；(d) 層6 對斜線方向威脅額外降權＋層7 己方進攻 30% 機率放棄斜線雙威脅構線。同時新增 `OrdinaryPlayerPolicy`（無 VCF/VCT 搜索、只有基本反射動作）作為「普通玩家」統計基準，改問「L4 對普通玩家的 Boss 勝率」而非「玩家對 L4 的勝率」，這才是「見習」難度真正該驗收的方向。

**第一輪（直接套用使用者裁決的字面數字）**：`skipOpenThreeChance=45%`、`diagonalOpenThreeSkipBonus=+15pp`、`blockSlipChance=10%`、`singleLineOnlyChance=30%`，層3完全移除。用真實 API 跑 N=200：**L4 對普通玩家 Boss 勝率只有 7.5%**（普通玩家 185/200 勝，且 92.5% 的對局在玩家自己的第 5 手就結束——幾乎是「見習魔王完全不會防守」）。

**根因分析（複合效應，而非任一單一旋鈕出錯）**：層3 一旦完全移除，層6（擋活三）就變成阻止玩家獲勝的**最後一道防線**——因為活三一旦被放過而長成活四，L4 沒有任何後續手段能擋（活四兩端皆勝，擋一端另一端仍會贏，這正是層3存在的原因）。這代表 L4 的存活率約等於 `(1-有效跳過率)^N`（N＝整場對局中玩家嘗試構築活三的次數）。45% 的跳過率單獨看不誇張，但疊加「層3=0%攔截」之後，複合到 N≈3-5 次嘗試就足以讓存活率崩潰到個位數百分比。這是兩個各自看起來溫和的放水旋鈕**相乘而非相加**的典型陷阱。

**統計方法論 bug（同一輪發現，非校準本身）**：初次量測用的 `simulate()` 沿用了參考玩家統計既有的「每格位重試至多3個候選seed」機制——這個機制對參考玩家統計是合理的（保護統計不被單一難搞 seed 冤枉一個「原本會贏」的強玩家），但套用到普通玩家統計上會**結構性地對玩家有利**：重試只在玩家「輸」的時候觸發，等同讓普通玩家享有 best-of-3。已修正：新增 `simulateSingleAttempt()`，普通玩家統計改為單次測量，不重試（`backend/src/test/java/com/gomoku/steps/pve/BossDuelStatisticsSteps.java`）。

**第二輪（下修三個機率旋鈕，層3移除本身維持不變）**：用一個繞過 Spring/HTTP/DB、純記憶體對局的 scratch harness（`ScratchL4CalibrationTest`，校準完成後已刪除，不在交付範圍內）快速跑 N=1000 迭代校準，找到 `skipOpenThreeChance=22%`（原 45%）、`diagonalOpenThreeSkipBonus=+8pp`（原 +15pp）、`blockSlipChance=5%`（原 10%）；`singleLineOnlyChance=30%` 未變（此旋鈕只影響 L4 自身進攻，不影響防守存活率，未參與複合效應）。真實 N=200 API 統計結果：

| 統計對象 | 目標門檻 | 實測數字 | movesUsed p50 | movesUsed p90 |
|---|---|---|---|---|
| L4 vs 參考玩家（`ReferencePlayerPolicy`） | 玩家勝率 ≥70% | **100%**（200/200） | 7 | 8 |
| L8 vs 參考玩家（未變動，回歸確認） | 玩家勝率 ≥45% | **100%**（200/200） | 16 | 21 |
| L4 vs 普通玩家（`OrdinaryPlayerPolicy`，單次測量） | **Boss 勝率 ≥60%** | **64.5%**（129/200） | 6 | 6 |

驗收指令：`docker` sibling containers（`gomoku-test-pg`/`gomoku-test-redis`）+ `mvn -o test`，`backend/src/test/java/com/gomoku/steps/pve/BossDuelStatisticsSteps.java`（`specs/features/pve/Boss對弈統計驗證.feature`），全綠；完整回歸 `RunCucumberTest` 333/333 + `BossAiPolicyTest` 12/12（新增 6 個案例：層2手滑統計、層3 profile flag、層6 斜線加碼統計、層7 斜線雙威脅避讓統計）+ 既有 `ManualSpotCheckPrinter` 1/1，共 346/346。

**誠實聲明（第二輪校準）**：

1. **層3的移除是使用者裁決的無條件項目，本輪未因統計不達標而回補**——所有下修都發生在機率旋鈕（層2/6/7），符合任務要求「不達標就繼續調(1)的旋鈕」的授權範圍，且保留了「見習魔王完全不會預判」這個質變特徵。
2. **22%/+8pp/5% 這組數字比使用者原始裁決的字面值（45%/+15pp/10%）低不少**——這不是不服從裁決，而是裁決本身內部有一個複合效應的隱藏假設（各旋鈕效果獨立可加）沒有被驗證，本輪校準把裁決的「方向」（放水、偶爾失誤）保留，只調整了「幅度」以符合裁決同時給出的驗收數字（L4 對普通玩家 Boss 勝率 ≥60%）。若使用者認為 22% 仍不夠貼近「45%」的原始語感，可以接受 60% 門檻本身調整（例如降到 50%）來換回更高的跳過率，這是設計取捨，本文件不擅自替使用者做這個決定。
3. **64.5% 高於 60% 門檻的margin不大**（4.5pp，N=200 下約 1.3 個標準誤差）——快速校準 harness 在 N=1000 下測得的真實勝率約 62-66%，屬於統計上合理但不特別寬裕的margin；若未來正式驗收用不同 seed 集合重跑出現臨界失敗，下一步應優先review `skipOpenThreeChance` 是否需要從 22% 降到 20% 左右，而非重新引入層3。
4. **L4 vs 參考玩家從 97.5% 升到 100%**——這是本輪防守全面弱化的直接結果，方向正確（見習魔王對「真的會強制手順」的玩家應該幾乎必敗），且與 L4 vs 普通玩家 64.5% 形成清楚對比，量化驗證了「見習」難度的核心賣點：能唬住新手、擋不住老手。

### 6.5 對弈公平性修正＋L4層3小機率回補（2026-07-09 三度執行紀錄）

**起因**：使用者評論驅動的三項修正之一——現行「手數耗盡未分勝負→FAILED」（§1.5，L8 模擬耗盡率 44.2%，見 §1.7）且只有玩家有手數配額、Boss 每手免費，雙方零失誤卻讓玩家獨自承擔「下不完」的全部責任，判定整個 run 敗（`LOST`）並沒收，這對玩家不公平。使用者裁決：手數耗盡且雙方皆未連五時改判 **`DRAW`**（和局），不沒收 run、不計敗，該關可原地無限次重試（每次重開盤面/Boss AI RNG 重新隨機）。同批任務並要求把 §6.4 對 L4 層3（阻止玩家形成活四）「完全移除」的緊急放水，改為 **8% 機率執行**——理由：手數耗盡不再是玩家的全責/末日結局後，L4 不再需要靠「完全零預判」才能對普通玩家維持可打性，保留一點點漏網之魚的機率，避免固定死角被套路、維持長期新鮮感。

**實作**：

- 新增 `PveEncounterStatus.DRAW`＋`PveEncounterEventType.ENCOUNTER_DRAWN`；`PveEncounter` 新增 `attemptNumber`（重試序號，預設1）＋`drawnAt`。
- `PveChallengeService#settleDuel` 的「手數用盡」分支：不再 `setStatus(FAILED)`／`run.setStatus(LOST)`，改為 `setStatus(DRAW)`＋發布 `ENCOUNTER_DRAWN`，**完全不碰 run 狀態**（run 保持 `IN_PROGRESS`）。
- 新增 `PveChallengeService#retryDuelEncounter`（`POST /pve/encounters/{id}/actions/retry`，DUEL限定、狀態須為DRAW）：軟刪除舊 encounter row，透過既有 `createEncounter` 為同一 sequence 建立全新 encounter（新 encounterId），`attemptNumber+1`。DB 層需要 **V6 migration**（`V6__pve_duel_draw.sql`）：① `status` CHECK 約束加入 `DRAW`；② 新增 `drawn_at`／`attempt_number` 欄位；③ **把 `uk_pve_encounters_run_sequence` 從全域唯一索引改成 `WHERE is_deleted = false` 的 partial unique index**——原索引不分 `is_deleted` 一律唯一，會擋下「軟刪除舊 encounter 後為同一 sequence 插入新一列」這個重試操作的本質需求；④ `pve_encounter_events.event_type` CHECK 約束加入 `ENCOUNTER_DRAWN`。
- **踩雷記錄（真 bug，已修）**：`retryDuelEncounter` 第一版直接 `encounter.setDeleted(true); encounterRepository.save(encounter);` 接著 `createEncounter(...)`（內部也是 `save`），統計測試（N=3 連續 DRAW→retry 迴圈）跑出 `duplicate key value violates unique constraint "uk_pve_encounters_run_sequence"` 500 錯誤——根因是 **Hibernate 的 flush 順序固定「所有 INSERT 先於所有 UPDATE」，與程式碼呼叫順序無關**：即使 Java 碼先呼叫舊列的 `save()`（UPDATE）再呼叫新列的 `save()`（INSERT），實際 flush 到資料庫時 INSERT 先執行，此時舊列在資料庫裡仍是 `is_deleted=false`，partial unique index 瞬間看到兩列存活的 `(run_id, sequence)`，插入失敗。修法：軟刪除舊列後改用 `encounterRepository.saveAndFlush(encounter)` 強制立即落地，確保 INSERT 執行前舊列已經 `is_deleted=true`。此 bug 只有在「同一次 HTTP 請求內先刪後插同一唯一鍵」這種模式才會暴露，單元測試/單次重試無法重現，必須靠**連續多次重試**的整合測試（N次DRAW→retry迴圈）才抓得到。
- **RNG 不決定性重播修正**：`duelRunSeed(run, encounter)`——`attemptNumber<=1` 時沿用 `run.getSeed()`（保留既有「同seed同手數必重現」NFR-1）；重試後 `attemptNumber>1` 時混入重試序號（`run.getSeed()+":retry"+attemptNumber`），確保 `BossAiPolicy.nextMove` 的機率旋鈕（跳過活三/手滑/預防性攔截...）在重試後不會因為「movesUsed 歸零→bossMoveNumber 重新從1算起」而與上一次嘗試在同一手數上擲出完全相同的骰子結果。
- `BossAiPolicy.Profile`：`preventsOpenFourFormation`（boolean）改為 `preventOpenFourChance`（double）；`APPRENTICE` 從 `false`（0%）改為 `0.08`（8%），`TRUE_DEMON` 從 `true` 改為 `1.0`（語意不變，恆定執行）。RNG purpose 新增 `"boss-ai-prevent:"+sequence+":"+bossMoveNumber`，與其餘旋鈕獨立擲骰。

**測試覆蓋**：

- `specs/features/pve/魔王對弈.feature` 新增 6 個場景：手數耗盡判DRAW＋run不受影響、DRAW後呼叫重試（斷言新encounter/舊encounter 404/run不受影響）、連續3次DRAW→retry迴圈（斷言run金幣/已抵達關卡序號不變，即本次踩雷記錄的 bug 就是被這個場景抓到的）、非DRAW狀態重試被拒(422)、PUZZLE關重試被拒(422)。

1. **層3回補到8%沒有讓「見習」難度失守**——65.0% 穩穩落在 55–70% 目標區間中段，且與 §6.4 校準時測得的 64.5%（層3=0%時）幾乎持平（+0.5pp），證實「手數耗盡不再是玩家全責」這個前提變了之後，層3從0%小幅回補到8%對L4實際強度的影響很小——這符合預期：8%仍是遠低於L8的100%，多數對局仍在L4完全不評估這一層的狀態下進行。
